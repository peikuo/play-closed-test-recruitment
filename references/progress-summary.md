# Communication and reciprocal-progress summaries

At the end of every interactive or scheduled work round, persist verified events to the private ledger and regenerate the following views from that ledger. A round includes interrupted, partial or failed work. Use the user's timezone, record generation time and checked/unchecked scope, and preserve earlier successful evidence. Never refresh an observation timestamp merely because a table was regenerated.

Keep these runtime views outside public repositories and release packages. Summarize relevant communication without quoting private messages or storing member emails, credentials or private screenshots. Use stable contact IDs/public handles; merge cross-channel identities only with evidence. Public thread links and sanitized local evidence references may support entries. The examples below are templates, not real contacts or activity.

## 1. This round's communication

| Time | Contact / app | Channel / public thread | Our action and concise topic | Their relevant response | Delivery / evidence | Next action / owner |
|---|---|---|---|---|---|---|
| [time] | [public handle / app] | [channel / public URL if available] | [invitation, eligibility question, install notice or feedback summary] | [sanitized reply summary, no new reply observed, or not checked] | [draft / sent text verified / attachment verified / failed / unknown; source and time] | [necessary next action / AI, user or counterpart] |

Include all contacts actually handled in the round; use separate rows for materially different events. Do not label a draft as sent, a preview as attachment delivery, or an inaccessible channel as no reply. If nothing was sent or received, record that explicitly with the actual checked scope rather than inventing a conversation. Keep earlier exchanges in the ledger history, not repeated verbatim in every round report.

## 2. Full reciprocal progress

Cover every tracked contact, including waiting, refused, blocked and unmatched contacts—not just this round's changes. Use separate stage states in each grouped cell; installation, launch and feature trials must remain distinguishable. Split a wide view into two tables keyed by the same contact ID when necessary.

| Contact / app | Agreement | Our group / Play opt-in | Our install / launch / functional trial | Our feedback / screenshot delivery | Their group / Play opt-in | Their install / actual use / feedback | Last successful evidence / freshness | Blocker / next action / owner |
|---|---|---|---|---|---|---|---|---|
| [contact ID / public handle / app] | [pending / directly agreed / declined] | [each stage separately] | [each stage separately; actual trial scope] | [text and attachment separately] | [each stage separately] | [each stage separately] | [source + original verification time; not rechecked if applicable] | [specific next step and responsible party] |

Use explicit labels such as verified, counterpart-reported, user-reported, pending, blocked, not checked or unknown. Use no only where evidence establishes absence; missing evidence is unknown. Retain corrections and refusal/moderation flags. A developer's promise is not completed testing, and our successful install does not establish their reciprocity. Do not request unnecessary new information just to fill cells.

## 3. Overall totals and human next steps

Report a dated snapshot with clear units and sources:

- Outreach: unique developers contacted, direct agreements and outstanding invitations. Count one author once across apps/threads; do not count drafts or repeated messages as new contacts.
- Our work: distinct apps opted into, installed, launched and functionally tried; feedback text delivered and screenshots delivered. Use separate totals and distinguish AI observations from user reports. Do not count repeated launches as new apps or partial trials as comprehensive tests.
- Counterpart work: matched group members, self-reported Play participants, individually verified opt-ins, reported/verified installs and actual-use/feedback evidence. Keep reported and verified figures separate; do not add overlapping evidence categories together.
- Platform progress: the latest Console count or lower bound, its verification time, continuous-participation eligibility, the user's buffer target and remaining verified gap when calculable. Group membership totals must not substitute for Play totals; disclose owner inclusion and unmatched members. Stale or unavailable Console evidence means the current gap is unknown.
- Next steps: outstanding links, eligibility/install blockers, pending screenshots/feedback, sustained human testing and required reviews. Assign each to AI, user or counterpart without inventing dates or sending reminders automatically.

Conclude interactive rounds with the communication changes, full current progress table (split for readability if needed), totals and actionable next steps. For large rosters, save the complete private table and link it in the user response alongside changes and totals; do not silently omit pending contacts. Scheduled runs save the same local views but notify only when the configured meaningful-change criteria are met. These summaries are for the user, not automatic messages to test partners.
